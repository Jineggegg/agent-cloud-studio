# 版本核对与任务恢复

## 版本与运行状态

在「设置 → 连接」查看以下信息：

- **这个浏览器**：当前标签页实际加载的构建。服务器更新后，旧标签页仍可能是旧版。
- **已部署前端**：服务器 `dist/build-info.json` 记录的构建。
- **正在运行的后台**：进程启动时固定读取的后端构建信息，不随源码目录或磁盘后续变化而更新。
- **当前代码目录**：当前 checkout 的分支、提交和未提交改动。
- **GitHub 最新提交**：origin 仓库默认分支的实时查询结果，短暂缓存；不可访问时明确显示无法检查。

提交不同只代表版本不同，不能单凭提交号判断谁领先。GitHub 已合并也不代表已部署。面板不拉取代码、不更新软件、不重启服务。

`npm run build` 在前后端构建开始时记录版本。没有 `.git` 的导出包可携带完整 40 位 SHA 的 `RELEASE_COMMIT`；这只提供来源提交，不能证明导出后未被修改。旧构建没有标记时显示未记录，开发页面不伪装成生产构建。

## 消息送达与人工续接

聊天发送使用客户端生成的 `requestId`。后端先持久化接收记录，再发送接收回执和启动执行。重复提交相同请求只返回原接收记录；相同 ID 对应不同内容或执行选项时拒绝执行。

确认前保留输入和附件。断网或未收到回执时显示「送达待核对」，重连只核对状态；用户可主动核对后重试原请求，沿用相同 ID。手动重试也先检查送达接口：已接收则直接恢复回执，旧后台不支持接口或核对失败时不重发。确认旧消息不会清空之后编辑的新草稿。当前标签页的待确认记录通过 `sessionStorage` 保留，以便刷新后核对；浏览器存储不可用或清除后，不能保证仍有客户端待确认记录。

启动时将上个进程尚未结束的记录标记为中断，**不自动重跑**。失败或中断记录在对应项目、会话内供用户查看：

1. 查看已有会话记录和原始请求，核对文件、部署等操作是否已生效。
2. 「准备继续」只填写可编辑草稿，由用户再次发送后创建新执行；不重放旧工具授权。
3. 「标记已处理」只处理提醒，不执行任务。

一个恢复记录只允许一个新执行领取，避免两台设备同时续接。系统先创建稳定的工作台会话 ID，再接收执行；模型自己的会话历史尚未生成时，执行账本仍保留原始输入供核对。

排队和定时任务在同一数据库事务中领取并创建执行记录。定时任务的 `claimed` 表示已接收、执行中，成功结束后才标记 `sent`，失败标记 `failed`。重启前已领取但结果不确定的任务进入人工核对；尚未领取的定时任务保持原调度方式。

这不是恢复模型进程的内存，也不是回滚已经发生的外部操作。当前保证覆盖 Studio 统一聊天调度入口；独立终端、SSH/tmux 和 DeepSeek 独立聊天不在该执行账本内。

## 接口与部署

- `GET /api/studio/runtime`：认证后的只读版本状态。
- `GET /api/task-recovery?projectPath=...&sessionId=...`：当前用户的待核对执行；`unassigned=true` 为兼容性的无会话筛选，当前所有已接收任务都有工作台会话 ID。
- `GET /api/task-recovery/requests/:requestId`：当前用户的送达记录。
- `POST /api/task-recovery/:runId/resolve`：标记已处理，不调用 provider。
- WebSocket `chat.send` / `chat.edit-send` 携带 `requestId`，收到 `run-accepted` 后确认接收。续接另带 `recoveryOfRunId`。重连游标由 `runId + seq` 共同标识。

本次包含后端与数据库新增表，需要部署后端并重启才生效。发布前使用 SQLite backup 保存一致的数据库副本，确认运行中的任务已结束或接受其进入中断核对，再发布经过验证的完整构建。保留前一构建及数据库备份。旧版页面没有客户端 requestId 时仅兼容原发送方式，无法获得完整重试防重保证；发布后应重新载入页面。

单元测试和浏览器尺寸测试不替代真实 iPhone/iPad 在锁屏、切网、后台挂起后的验收。
